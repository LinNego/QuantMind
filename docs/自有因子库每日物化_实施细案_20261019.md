# 自有因子库每日物化 · 实施细案与交付（2026-10-19）

> 目标：让推理/训练所依赖的**全部自有因子库**在每个交易日夜间自动补齐，
> 存量与新模型不再因「库停在旧分区」而读到 NaN。
> 原则：先验证口径 → 再回填 → 再上每日调度；全程串行、可观测、失败可重试。
> 状态：**代码已交付**（2026-10-19 夜），生产回填与 cron 安装见 §五。

## 一、现状（实测）

### 1.1 推理实际读哪些库

模型字段契约的**唯一来源**是模型 `metadata.json` 的 `factor_field_sources`
（与读侧 `QuantDBFactorReader` 同语法）：

- 值形如 `"库:列"` → 读副库；
- 值是不带前缀的裸列名 → 读**锚库**（`metadata.factor_source`）；
- 无来源的特征列（如 qlib Alpha158 的 `KMID` 系）→ `unmapped`，不设闸。

为什么不能按「列名出现在哪个库」猜：同一列名可能同时存在于 `factor_defs` 与
`cand_factors`，模型实际读的是自己的锚库；猜错库会让探针在错误的库上判定覆盖。

### 1.3 口径要点（已核）

- **统一 staging**：生产者写 `_staging_<库>`，正式库只经**列级合并**改动。
  原因：factor1300 的 `merge_partials` 会**整日覆盖**最终文件，多子集运行会互相抹列。
- **尾窗预热（2026-10-20 修正）**：清单里的 `window` 只是单层窗口，嵌套 rolling
  的需求是**相加**的（`REF(504)+TSRANK(504)=1008`）。实测需求：factor_defs 全库
  最大 1008（`risk_fac_momentum`），次大 756；factor1300 全库最大 2420
  （`f13_0020`），其中 41 条 ≤1220。因此第一遍仍跑 900/400 日全库，**第二遍**
  用独立 staging `--only` 重算超出部分：factor_defs 1 条（1008 日）、factor1300
  41 条（≤1220 日，预热取最长需求 + 8 日余量）。超过 1300 日的 6 条非必需因子
  （`f13_0020/0057/0058/0523/1040/1041`）本轮延后，见 §六。
  生产者会多算并写出目标日前一个交易日，供重叠日探针比对。
- **cand_factors 无独立公式**：238 个因子列是 factor_defs 的精确子集（09-18 对拍
  max|diff|=0），其余列为 `symbol/date/OHLCV/amount`（来自 `daily_backward`）。
  因此每天在 factor_defs 落盘后派生即可，天然同步。
- **gap_mined**：38 列 L2 二阶变换 + 5 列非 L2。`MG2_BALCHG_3M` 依赖两融分区，
  当晚未落盘时整列为 NaN 属**已知 T+1 滞后**（`EMPTY_TOLERANT_COLUMNS`），
  其余列缺数据按致命处理；次日回补窗口会自动重算该日。
- **rd_mined 双根**：`rd_mined_materialize --refresh-*` 写 CUSTOM 根，
  `promote_rd_mined.py --register` 镜像到 quantdb CN 并刷新字段登记。
  `--publish` 决定哪些因子进入 CN 训练目录，是**人工目录发布**，不得进每日链。
- **factor1300 仓外**：脚本在 `data/factor1300/scripts/f1300_compute.py`
  （`data/` 是宿主持久化卷）。2026-10-19 已补 `--start-year` 参数，
  `load_kline(start_year=...)` 在 DuckDB 侧按年过滤，尾窗运行显著降内存。
  该目录不在 git 内，脚本变更需另行备份。

### 2.2 日期规划

- 目标日 = `daily_forward` 最新分区（可用 `--target` 覆盖）。
- 每库：正式库最新分区之后的交易日全部补；空库且未给 `--since` 直接拒绝
  （**不允许隐式全量回填**）；单次最多 60 个交易日。
- **自动回补**：近 `--repair-window`（默认 10）个交易日里，某必需列
  「前一日有值、当日全空」→ 该日加入本轮重算（典型：两融 T+1、上游当晚才到齐）。
  结构性全空列不触发；回补日超出窗口后自然老化，避免每晚无限重试。

### 2.3 重叠日探针

生产者多写目标日前一个交易日（**不并入正式库**），把「有限预热窗复算值」与
「正式库全历史值」比对：

- 硬性问题（`ok=false`）：必需列由有值变全空、staging 缺必需列、**覆盖塌陷**
  （staged 非空值 < 正式库一半）、**秩相关跌破 0.9**、标的缺失 >5%；
- 相对误差只作信息上报（`share_rel_gt`）。2026-10-20 实测：qfq
  （`daily_forward`）每晚按最新复权因子**整段重写**，重叠日的相对误差最高
  0.66，但全部漂移列的秩相关 0.985~0.9999——拿相对误差做硬闸会天天误报。
  结构性错误（公式语义、单位切换、取错列）才会让秩相关掉下来。
- 非必需列整列空 → 信息上报（长窗因子在第一遍短预热下天然为空，由第二遍补齐）。
- **探针前置于合并**：探针 `ok=false` 或生产者 rc≠0 → 本库**不合并**、状态 failed、
  保留 staging 供排查（下一轮 `prepare_staging` 清理）。旧实现先合并后探针，
  预热不足的空列/漂移值会先落进正式库。
- 漂移只比对数值列：`time/date` 是 timestamp，旧实现对全部公共列
  `astype("float64")`，真实分区上必抛 `TypeError`（已用 factor_defs/gap_mined
  真实分区回归）。
- **两遍各自探针、各自合并**：第二遍写 `_staging_<库>_long`（与第一遍隔离，
  防止 factor1300 的 `merge_partials` 整日覆盖互相抹列）。第一遍的必需列集合
  剔除全部长窗列（本轮故意留空，不能判成预热不足）；第二遍只用长窗必需列做探针。
  两遍合并后取最坏终态。2026-10-20 长窗档实测：`f13_0654` 在 400 日预热下
  秩相关 0.844，1240 日预热下与官方全历史值重合 **1.0000**（60 标的冒烟，
  `f13_0261/0390/0422/0423/0645/0652` 同为 1.0000）。

合并时 `skip_empty_columns=True`：staging 里整列空的列**不覆盖**正式库的存量值
（否则短预热尾窗会把长窗列写成 NaN）。

### 2.4 合并与行集

- `merge_day_columns`：按 `symbol` 对齐，只覆盖传入列；正式库缺该列时新增；
  正式库缺该日分区时以 staging 为模板**建全宽分区**（缺列 NaN）。
- **部分标的保护**：staging 只覆盖部分标的时（单日补数/单批 `--only`），未被
  覆盖的标的保留正式库原值，绝不因 `reindex` 抹成 NaN；整列类型尽量保持原 dtype。
- **模板回退**：最近 `dt=` 目录若只有空壳（SIGKILL 残留、无 `data.parquet`），
  继续向前找有效分区，避免新日建出 staging 的窄 schema。
- **临时文件**：`.data.parquet.tmp`（不以 `.parquet` 结尾）。读侧按
  `dt=*/*.parquet` glob，旧名 `data.parquet.tmp-merge.parquet` 会被读成第二个
  分区（重复行/错 schema），且崩溃后永久残留。
- **新日标的完整性闸**：正式分区不存在时，当日全市场标的数 < 上一分区 90%
  （或 `daily_backward` 无当日分区）→ 跳过该日合并、状态 partial。新日行集一旦
  落盘就无法补标的，宁可次日重跑。
- **修复快照**：合并到已存在的正式分区前，先复制到
  `<quantdb>/6_ml_datasets/_repair_backup/<库>/dt=<日>/`（首次快照保留，不覆盖），
  供人工回滚。
- 目标日标的行集 = `daily_backward` 当日全市场；**l1 例外**：用生产者自己的股票池
  （5211 行 vs 全市场 5574），因为 l1 历史分区就是该池，强行注入全市场会凭空
  多出无因子值的行。

### 2.5 状态与告警

- 日志：`logs/keepers/factor_materialize_<run_id>.log`（子进程全量输出）。
- 状态：`<quantdb>/6_ml_datasets/_materialize_status.json`：
  `ok`、各步 `status/dates/elapsed_s/child_peak_rss_mb/coverage/manifest`，
  保留最近 30 轮。
- 告警：失败/部分完成/内存跳过/锁占用跳过/alpha 等待超时 → QQ
  （`scripts/push_notify.py`）；成功只记日志。状态文件早于开跑时间（硬崩/OOM）
  会在告警文案里标注「状态陈旧：本轮未落盘」。
- 覆盖闸门按 `gate_columns()`（已剔除结构性全空列）逐目标日检查至少一个非空值；
  两融类已知 T+1 列（`KNOWN_LAG_COLUMNS`）只报「延后」，不判失败。
- 终态判定：生产者 rc≠0 或重叠探针 `ok=false` → **failed**；缺日/新日标的不足/
  `MANIFEST.json` 中命中模型必需列的求值失败 → **partial**；否则 ok。
  覆盖缺口同样把 ok 降级为 partial。
- 单库异常隔离：步骤抛异常只落该库 failed，后续库照跑、状态文件照写。
  空库未给 `--since` 也按库隔离（failed + 继续），不再掀翻整轮。

## 三、调度

### 3.1 时刻

**2026-10-20 用户拍板：改为 JST 23:00（北京 22:00）起跑**，用户口径是 QuantDB
数据一般在 22:00 前更新。原 `10 4 * * 2-6` 方案未安装、已作废。

实测本机 A 股同步调度存于 Redis `quantmind:sync_schedule:A`（当前 `00:55`
容器 CST = `01:55` JST），故 23:00 起跑时目标日 = 当时最新日K（通常为前一
交易日），当晚新落盘的一日由次晚补。计划：

```
23:00 JST  本链起跑（先等 alpha 锁，上限 60 min → 内存闸）
~01:00 JST 快档六库收工（2026-10-20 首跑实测 1h49m，含 rd_mined 56m）
~01:30–02:30 JST 长窗第二遍收工（额外 ~1–1.5h）
01:55 JST  quantdb 次日分区落盘（由次晚物化）
02:30 JST  alpha_library 全量刷新档期（本机内存闸常跳过）
08:50 JST  盘前池检查
09:00 JST  容器 08:00 CST 盘前推理
```

### 3.2 闸门

1. **flock 防重入**：`/tmp/.qm_factor_materialize.lock`；上一轮未完成直接跳过。
2. **等 alpha**：轮询 `/tmp/.qm_alpha_refresh.lock` 与 `/tmp/.qm_alpha_retry.lock`，
   占用则每 60s 重试，上限 `ALPHA_WAIT_SECONDS`（默认 3600s）。
3. **内存闸**：可用内存 < `MIN_MEM_GB`（默认 11，按实测峰值 8.7/10.2GB 定）
   先有界等待 1800s；仍不足则跳过并推 QQ（每日唯一档期，静默跳过 = 次日推理缺特征）。
4. **长窗遍独立闸**：第二遍开跑前再查可用内存（`LONG_PASS_MIN_MEM_GB`，默认 11）
   与 alpha 补池锁；不足只跳第二遍、状态 partial（见 §5.2）。
5. **行情空目录**：`daily_forward` 无分区 → 跳过并推 QQ。

| 快档实测峰值 | factor_defs 3.7GB（907 日）、factor1300 8.7GB（405 日） |
| 长窗峰值实测 | **10.19GB**（1234 日 × 5579 标的，172 帧，8m20s；`--dry-run --only f13_0645,f13_0261 --bank-size 8`） |
| 标定结论 | 600/1200 标的峰值 3.05/3.27GB → 固定开销 ~2.8GB，其余随标的数增长；早期按快档合并峰值线性外推的 26GB **高估 2.5 倍** |

CIFS slab 不可回收（SUnreclaim），`drop_caches` 无效；释放需卸载未用 NAS 共享
或重启宿主（**均需用户授权/root，未执行**）。按实测落地两道新闸：

1. **整轮起跑闸**降为 11GB（`scripts/factor_materialize_daily.sh` 的
   `MIN_MEM_GB` 默认值）——旧默认 24GB 在本机（长期 ~12GB 可用）会让日更链
   永远跳过；
2. **长窗遍独立闸** `LONG_PASS_MIN_MEM_GB=11`（orchestrator）：内存不足或
   alpha 补池锁被占用时**只跳过第二遍**，第一遍结果照常合并，状态记
   `partial`，缺列由下一轮近窗回补自愈；长窗遍同时用 `--bank-size 8` 降低
   求值驻留。

实测峰值 10.19GB，起跑时 12.5GB 可用 → 余量约 2GB；若 alpha 补池重试在链
中途起来（24GB 峰值），独立闸会拦住第二遍而不是与它叠加。

## 六、风险与边界

- **内存**：夜间与 alpha（24GB 峰值）、补池重试链、训练容器共享 60GB；快档用
  `--bank-size 30`、长窗遍降到 8，`nice -n 10` 降优先级；整轮闸不足即跳过并
  告警，长窗遍闸不足只跳第二遍（§5.2）。宿主机当前受 CIFS slab 泄漏限制
  仅 ~12GB 可用，峰值 10.19GB 意味着余量约 2GB——**不要在长窗遍期间再起
  alpha/训练**。
- **写权限**：库目录存在 root 属主历史（alpha 曾因 PermissionError 白跑）；
  合并失败会以状态/告警暴露，修复：`sudo chown -R zbox:zbox <库目录>`。
- **factor1300 长窗列**：按公式 AST 的复利预热口径（`window` 字段低估），
  全库 47 条 >405 日；其中**模型契约内**的是 `f13_0261`（960）、
  `f13_0390/0422/0423`（480）、`f13_0645`（1220），已由第二遍
  `--only` 覆盖。其余长窗列若不在契约内，新日期上可能无值
  （`skip_empty_columns` 保证不覆盖存量）；超长 6 条见下条。
- **仓外脚本**：factor1300 生产者与 `data/` 同生命周期，仓库重建不含它；
  已补的 `--start-year` 变更需随备份保留。
- **rd_mined 发布边界**：每日只 `--register`；`--publish` 是人工目录发布，
  绝不进 cron。refresh 单因子超时会让整体 rc≠0，但目标日分区已落盘（实测
  120/122）时仍 promote 并记 **partial**；只有目标日分区没写出来才判 failed。
- **factor1300 超长窗 6 条**：`f13_0020`（2420 日）、`f13_1040`（2400）、
  `f13_1041`（1920）、`f13_0057/0058`（1680）、`f13_0523`（1440）不在当前
  模型契约内，日更链延后（状态里 `deferred_long` 可见）。补齐另起每周长窗档
  （`--start-year 2019 --max-days 2430`，网格约为日更的 6 倍，RSS 预计
  45GB+，须与 alpha/训练错峰，默认不自动跑）。
- **第二遍内存**：factor1300 长窗网格 1234 日（1234 日 × 5579 标的、172 帧、
  `--bank-size 8`）2026-10-20 实测峰值 **10.19GB、8m20s**（理论 25~30GB 的
  旧估算已按实测修正）；快档峰值 8.7GB。23:00 起跑时 alpha 尚未开档，长窗遍
  有独立内存闸（11GB）与 alpha 锁检查；02:30 的 alpha 档期若与长窗遍重叠，
  alpha 自身 30GB 内存闸会先等后跳，长窗侧由各自告警兜底。
- **不改**：alpha_library 现有 cron、CUSTOM 调度、alpha_refresh_retry 三档、
  训练/推理读路径。
