# 通达信桥 · 行情数据面机构级架构细案

日期：2026-10-22
状态：**待拍板**（先选架构，再开工）
范围：13 号 Windows 机上的通达信交易桥（`C:\new_tdx_mock\PYPlugins\bridge-windows`）、TQ 17709 行情/交易会话、QuantMind 后端数据消费侧。
硬约束：**只用通达信数据**（其他渠道不可用）；实盘交易不能因数据采集增加失败风险；单 Windows 机、单 TQ 会话。

## 1. 侦察结论（2026-10-22 实测）

| 项 | 实测值 | 备注 |
|---|---|---|
| 全市场 `get_pricevol(5581)` | 2.74–3.35s / 次，响应 400KB | 单次可覆盖全 A |
| `get_market_data(1m)` 批量 | 200 只 0.05s；1000 只 0.06s | SDK 内部按 100/页分页 |
| `get_market_snapshot` 单股 | 33ms | 五档 |
| 并发：1 个 pricevol + 1 个 snapshot | snapshot **27ms** | TQ 17709 支持并发 |
| 并发：4 个 pricevol + 1 个 snapshot | snapshot **3635ms** | **桥的全局 Semaphore(4) 被打满** |
| pricevol 分块 500 只 | 70ms / 块 | 分块是控制占用的关键 |
| `subscribe_hq` | 单会话 **≤100 只** | SDK 硬限制 |
| `subscribe_quote` | SDK 注明“暂无实际功能” | 不可用 |
| pro-data（GP/BK/SC/GO/FN） | 桥误发 `field_list`，DLL 回 `no table_list` | 已修为 `table_list`，实测 ErrorId=0 |

**根因判断**：交易调用被数据调用堵住，不是 TQ 不行，而是桥把所有 TQ 调用塞进**同一个 4 槽信号量**；4 个大数据请求就能占满，快照/下单必须排队。

### 1.1 数据能力边界（2026-10-22 补测，决定“数据最优”的上限）

| 数据 | 可用字段 | 限制 |
|---|---|---|
| `get_pricevol`（全市场） | **LastClose / Now / Volume**（仅 3 字段） | 无成交额、无五档；5,581 只一次 2.7–3.4s |
| `get_market_snapshot`（单股） | 26 字段：Amount、Average、Buyp/Buyv×5、Sellp/Sellv×5、Inside/Outside、Open/High/Low 等 | 33ms/只；全市场轮询不可行 |
| `get_market_data(1d)` | OHLCV + Amount + ForwardFactor | 批量可用；收盘后取全市场日线可行 |
| `get_market_data(1m/5m)` | **实测返回空**（显式交易时段、count=-1、type=1、分页参数均试过） | 大概率缺客户端分钟数据包；待下载后复测 |
| `subscribe_hq` | 推送，最多 100 只/会话 | 只够热集 |
| `subscribe_quote` | SDK 注明“暂无实际功能” | 不可用 |

**结论**：只用通达信时，数据面最优只能做到分层，而不是“全市场全字段高频”：

1. **全市场 5s**：`pricevol` 的价/量 → 内存；用它**实时聚合 1m OHLC + 成交量增量**（成交额缺失）。
2. **热集 ≤100，3s**：`get_market_snapshot` 全字段（含五档/成交额），内存 + 落盘。
3. **日线全市场**：`get_market_data(1d)` 批量，收盘后落盘/入库。
4. **历史 1m**：需客户端下载分钟数据包后复测；不可用则以第 1 条的实时聚合为准。

## 2. 架构选型

### 候选

| 方案 | 结构 | 稳定性 | 改造量 | 结论 |
|---|---|---|---|---|
| A. 单进程优先级队列 | 桥内一个 TQ 仲裁器，trade > data | 中：数据 bug 可拖垮交易进程 | 中 | 不作为首选 |
| **B. 双进程 + 桥内双信号量** | 交易桥保留；新增独立采集器；桥内 trade/data 各 2 槽 | **高**：进程隔离 + 配额隔离 | 中 | **选它** |
| C. 中央 TQ 仲裁进程 | trade/collector → arbiter → 17709 | 最高 | 大 | 留作 B 不达标时的升级路径 |
| D. 消息总线 | Redis Stream/NATS 传数据 | 高 | 大 | 多市场/多消费者时再上 |
| E. gRPC/流式 | 替换 REST | 中 | 中 | 与 B 组合，非独立方案 |

### 选定：B —— 交易桥 + 独立数据采集器，桥内双配额

```
┌──────────────────────── Windows 交易机 ────────────────────────┐
│                                                                │
│  bridge-trade :8550                                            │
│   ├─ /plans/execute /orders/cancel /account /orders            │
│   ├─ trade_semaphore = 2   ← 只给交易/账户/委托查询             │
│   ├─ data_semaphore  = 2   ← 给行情数据（含采集器/热集/采集任务）│
│   └─ TQ 17709                                                  │
│                                                                │
│  tdx-collector :8560（独立进程，崩溃不影响交易）                 │
│   ├─ 全市场 pricevol：分块 500，5s 一轮                         │
│   ├─ 全市场 1m bars：分块 1000，60s 一轮                        │
│   ├─ 内存快照 + 1m 环形缓冲                                     │
│   ├─ 落盘：JSONL/SQLite（1m bars），收盘快照交现有 tdx_ingest    │
│   ├─ 只读 HTTP：/health /snapshot /bars /lag                    │
│   └─ 熔断：TQ 延迟/错误率超阈值 → 暂停采集，退避恢复             │
│                                                                │
│  Ubuntu QuantMind ── 交易走 :8550 ── 行情走 :8560（缓存优先）    │
└────────────────────────────────────────────────────────────────┘
```

**为什么不是 A**：数据和交易同进程，任何一次采集异常（解析大 JSON、内存峰值、线程泄漏）都可能把下单路径一起拖死。机构级第一原则是故障域隔离。
**为什么不是 C（现在）**：TQ 本身已被证明能并发（1 数据 + 1 交易 = 27ms）；把桥内信号量拆成 2+2 就能覆盖 4 个 TQ worker，额外加一个仲裁进程只会增加跳数和故障点。C 作为 B 的升级预案。
**为什么不用 QMT/其他数据源**：用户明确只能用通达信。

## 3. 交易面改造（bridge-trade）

1. **双信号量**
   - `trade_semaphore = 2`：`/plans/execute`、`/orders/cancel`、`/account/query`、`/orders/query`、`/sltp/*`。
   - `data_semaphore = 2`：`/api/v1/tdx/call` 的行情方法、热集轮转、`tdx_ingest`。
   - 交易调用永远不排队在数据调用后面；数据最多占 2 个 TQ worker，交易保留 2 个。
2. **方法分类表**（唯一出处）
   - trade：`order_stock`、`cancel_order_stock`、`query_stock_asset`、`query_stock_positions`、`query_stock_orders`、`stock_account`。
   - data：其余行情/财务/板块方法。
   - 分类在 `routes.py` 一处维护，`/tdx/call` 与专用端点共用。
3. **超时**
   - 交易调用 8s（保持）；数据调用按分块后的预期延迟设 15s，**禁止把 3s+ 的全市场调用放进交易槽**。
4. **可观测**
   - 每类调用记录 `wait_ms`（等信号量）、`exec_ms`、`sem_inflight`；`/stats` 增加 `semaphores: {trade: {inflight, waiting}, data: {...}}`。
   - 交易等待超过 200ms 打 WARN；超过 1s 打 ERROR（这是数据面挤占交易的早期信号）。

## 4. 数据面：tdx-collector

### 4.1 采集节奏（交易日 09:15–15:05）

| 数据 | 方法 | 分块 | 节奏 | 目的 |
|---|---|---|---|---|
| 全市场 L1 快照 | `get_pricevol` | 500 只/块，12 块 | 5s 一轮 | 最新价/累计成交量 → 内存 |
| 全市场 1m 聚合 | 由上一行的 5s 采样在采集器内聚合 | — | 每分钟封口 | 1m OHLC + 成交量增量（无成交额） |
| 热集全字段 | `get_market_snapshot` | 并行 2 路 | 3s 一轮（≤100 只） | 五档/成交额/内外盘 |
| 日线全市场 | `get_market_data(period=1d,count=2)` | 1000 只/块 | 收盘后一次 | 日线校验/补齐 |
| 历史 1m | `get_market_data(period=1m)` | — | 收盘后 | **待客户端分钟数据包复测**，不可用则只保留实时聚合 |
| 收盘快照 | `get_pricevol` 全量 | 1 块 | 15:31 | 交现有 `tdx_ingest` 落 PG |

- 采集器**只允许 1 个并发数据调用**（桥 data 槽另有 1 个给热集/采集任务）。
- 每块之间 `sleep(20ms)` 让出队列；检测到交易信号量有等待时，采集器暂停 200ms。
- 09:25–09:30、14:57–15:00 两个撮合窗口，采集器降为只采热集，避免任何大调用。

### 4.2 内存缓存

- `latest_snapshot: dict[str, dict]`：5,581 条 × ~20 字段，约 20–40MB。
- `bars_1m: dict[str, deque(maxlen=240)]`：今日分钟线，约 100–200MB。
- 元数据：`last_snapshot_ts`、`last_bar_ts`、`last_error`、`lag_ms`。
- 不做全量 5s 快照落盘（约 1GB/天）；只保留最近 15 分钟环形缓冲，供盘中特征/回放。

### 4.3 落盘

- 1m bars：**由 5s pricevol 采样聚合**（每分钟 12 个采样点 → OHLC；成交量用累计 Volume 差分），写入 `data/market_1m.db`（SQLite WAL，表 `bars_1m`，主键 `(trade_date, code, minute)`）；无成交额字段，用 `amount=NULL` 显式标注。
- 热集全字段快照：可落 JSONL/Parquet（≤100 只，体量小），保留最近 90 天。
- 日线：收盘后 `get_market_data(1d)` 批量校验；收盘全市场快照交现有 `tdx_ingest`（PG + parquet）。
- 历史 1m：客户端分钟数据包就位后，用 `get_market_data(1m)` 回填；在此之前只有实时聚合数据。
- 保留：1m bars 默认 90 天（约 3–5GB），由维护脚本清理。

### 4.4 读侧分发（关键：别的地方从这里拉）

- `GET /health`：`tdx_connected`、`last_snapshot_age_ms`、`last_bar_age_ms`、`inflight`、`lag_ms`。
- `GET /snapshot?codes=600519.SH,000001.SZ`：内存最新快照。
- `GET /bars?period=1m&codes=...&start=...&end=...`：今日/历史分钟线。
- `GET /lag`：数据新鲜度。
- 鉴权：独立只读 token（与交易 token 分离）；默认只绑 `127.0.0.1` + 局域网白名单。
- Linux QuantMind 新增 `TdxDataClient(COLLECTOR_URL)`；批量行情/分钟线一律读采集器，**不再直接打桥**。交易/账户仍走桥。

## 5. 稳定性设计

### 5.1 故障域

| 故障 | 影响 | 处置 |
|---|---|---|
| 采集器崩溃 | 行情缓存停更 | Windows 服务/计划任务自动拉起；交易桥不受影响 |
| 采集器卡死 | 快照 lag 增大 | 看门狗按 `/health` 15s 超时重启 |
| TQ 延迟升高 | 交易可能排队 | 采集器熔断：连续 3 次 >2s 或错误率 >5% → 暂停 30s，指数退避 |
| 桥 data 槽被采集器占满 | 热集/采集任务排队 | 采集器单并发 + 分块 ≤500；桥 data 槽 2 个 |
| 交易槽被占满 | 下单排队 | trade 槽 2 个独立；等待 >1s 告警 |
| TQ 会话掉线 | 行情/交易都断 | 现有 keepalive 自愈；两侧 `/health` 都报 `tdx_connected=false` |

### 5.2 配额与容量

- 桥：trade 2 + data 2 = 4（与实测 TQ 并发深度 4 对齐）。
- 采集器：1 个在途数据调用；每块 500 只；每轮 12 块 ≈ 0.84s TQ 占用 / 5s = 17% 单 worker。
- 全市场 1m：6 块 × ~60ms = 0.36s / 60s，可忽略。
- 网络：400KB/5s ≈ 0.64Mbps；LAN 充裕。
- 内存：<300MB；CPU：采集器 <10%（单核）。

### 5.3 SLO（上线判据）

| 指标 | 目标 |
|---|---|
| 下单 ack p99（Linux→桥 ack） | < 100ms；采集器开启后相对基线增幅 < 20ms |
| 撤单 ack p99 | < 100ms |
| 交易信号量等待 >200ms 的比例 | < 0.1% |
| 全市场快照 lag p95 | ≤ 5s |
| 全市场 1m bars 完整率 | ≥ 99.5% |
| 采集器可用性（交易时段） | ≥ 99.9% |
| TQ ErrorId≠0 比例 | < 0.5% |

### 5.4 kill criteria（不达标就回退/停方案）

- 采集器开启后下单 p99 增幅 > 20ms 或出现任何因等待导致的超时 → 立即停采集器，回退到单进程现状。
- 全市场快照 lag p95 > 10s 连续 10 分钟 → 降频到 10s 或停采集器。
- TQ ErrorId 比例 > 1% 或 TdxW CPU > 80% → 降频/熔断。
- 1m bars 完整率 < 99% → 排查分块/超时，不达标不上生产。

## 9. 风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| TQ 并发深度实际只有 2 | 中 | 2+2 配额不足，交易等待 | 先压测确认；保留 C 方案 |

| Windows 服务化引入新故障 | 低 | 进程起不来 | 先计划任务，稳定后再服务化 |

**回滚**：采集器是旁路，停进程即回退；桥的双信号量可配置回单信号量（配置项 + 重启），不影响交易语义。

## 10. 什么叫“最优”（结论）

- **架构最优（约束内）**：只用通达信、单 Windows 机、单 TQ 会话、实盘不中断——B（双进程 + 桥内 trade/data 双信号量）是当前工程最优折中。绝对最优不存在：单机单会话就是硬约束；要更强只能上方案 C 或第二台机器/第二个数据源。
- **数据最优（能力内）**：通达信的能力边界决定只能分层——
  - 全市场 5s：**只有价/量**（pricevol 3 字段）；
  - 热集 ≤100，3s：**全字段**（snapshot 26 字段，含五档/成交额）；
  - 日线全市场：全字段（1d 批量）；
  - 历史 1m：待客户端分钟数据包；否则只有实时聚合的 OHLC+量（无额）。
  - 若业务要求“全市场 + 五档 + 3s”，通达信单会话做不到；这是硬边界，不是实现问题。
- **性能**：全市场 pricevol 5s 一轮约 0.84s TQ 占用（17% 单 worker）；1m 由采样聚合，**不额外占用 TQ**；热集 100 只 × 33ms / 2 并发 ≈ 1.7s，可塞进 3s 周期；桥/采集器网络 400KB/5s ≈ 0.64Mbps。
- **稳定性**：交易/数据故障域隔离、双配额、分块、熔断、看门狗、SQLite WAL、bounded memory；仍需补的短板：
  1. `aiohttp.access` 每请求一行日志（生产已 1.5GB）→ 建议降到 WARNING，减少 I/O 与磁盘；
  2. 桥事件循环仍要解析 400KB 的 pricevol JSON；若后续成为瓶颈，采集器可直连 17709（去掉桥这一跳，但失去桥的鉴权/审计，需另行加 token）；
  3. 热集/采集任务/采集器共用 2 个 data 槽，数据侧可能排队（交易侧不受影响）；
  4. Windows 单点、无 HA；靠看门狗 + 心跳告警；
  5. TLS/分级 token 未做（Phase 3）。

## 11. 需要拍板的点

1. **历史 1m**：是否去通达信客户端「系统 → 盘后数据下载」补分钟数据包，然后复测 `get_market_data(1m)`？不补则只有采集器实时聚合的 1m（OHLC+量，无成交额）。
2. **全市场 5s 只有价/量**：业务是否接受？需要成交额/五档的部分是否限定在热集 ≤100？
3. **aiohttp access 日志**：是否降到 WARNING（减少 I/O 与磁盘；审计仍由 SQLite `tdx_log` 承担）？
4. **采集器链路**：默认走桥（保留鉴权/审计/双信号量）；若桥 JSON 解析成为瓶颈，再评估直连 17709（去一跳，但失去桥的审计）。
