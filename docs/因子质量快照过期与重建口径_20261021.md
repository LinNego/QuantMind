# 因子质量快照过期与重建口径（2026-10-21）

## 1. 用户现场

后台管理 → 模型训练数据集 → L1 因子：

```
就绪 · 分区文件 2,616 · 覆盖 2016-01-04 ~ 2026-10-14 · 已发现字段 110
质量快照 2026-09-19
评估期 2017-01-03 ~ 2026-09-17 · 2,359 交易日 · fwd_ret_5 · 指标匹配 110/110
[快照超过 30 天未更新]
```

用户疑问：「都快照超过 30 天未更新？没有更新？我都更新最新了啊」。

## 2. 事实核查

| 项 | 值 | 来源 |
| --- | --- | --- |
| 快照文件 | `6_ml_datasets/l1_factors/report/factor_report.json` | 容器内 `find` |
| 生成时间 | 2026-09-19 22:10:50（文件 mtime 同） | 快照 `meta.generated_at` |
| 快照评估期 | 2017-01-03 ~ 2026-09-17，2,359 日 | 快照 `meta.start/end/n_dates` |
| 盘上因子数据 | 覆盖至 2026-10-14（构建时已到 2026-10-20） | 分区目录 |
| 构建耗时 | 361.2 秒（8 workers） | 快照 `meta.elapsed_sec` |

**结论：数据确实更新了，但质量快照不会随之更新。** 二者是两条独立的链。

## 3. 链路真相

```
日更同步 quantdb_daily_sync.py
  → parquet 分区（6_ml_datasets/l1_factors/dt=*）
  → PG / Qlib 缓存 / 特征
        │
        │  ✗ 不触发
        ▼
因子报告快照 build_factor_report.py（离线构建产物）
  → report/factor_report.json（IC/ICIR/换手/单调性/胜率 …）
        │
        ▼
/fields 的 stats_meta ← training_stats.build_fields_stats（只读文件 + mtime 缓存）
        │
        ▼
后台「模型训练数据集」质量快照展示
```

- 日更同步**只**写行情/因子分区，不重建报告快照；
- 「质量快照」日期 = 快照 `meta.generated_at`；
- `STALE_DAYS = 30`：生成时间距今 > 30 天 → `stale=True`，前端显示橙标。

因此 2026-09-19 的快照到 2026-10-19 起必然触发橙标——**这是提示，不是同步失败**。

## 4. 本次发现的两个问题

### 4.1 过期提示没有给出下一步（已修）

`build_fields_stats` 只在「快照缺失/损坏」时给 `rebuild_hint`；快照存在但过期时
`rebuild_hint=None`，页面上只有一句「快照超过 30 天未更新」，用户无从知道
「数据同步不重建快照、要去因子研究报告页重建」。

修复：`training_stats.py` 在 `stale` 时补 hint：

> 快照为离线构建产物，数据同步不会自动重建；可在「因子研究 → 因子报告」页点「重建快照」

前端 `SourceVitalStrip` 本就在 stale 分支渲染 `stats_meta.rebuild_hint`，无需改动。

### 4.2 一键重建会静默缩短评估期（已修）

`service.start_build` 按注册表 `build_start` 拼 `--start`；构建器缺省 `--years 5`。
CN `l1_factors` 之前**没有** `build_start`（注册表只给 rd_mined / factor1300 /
cand_factors / features_daily / l1_batch1 配了起点），而盘上 L1 数据自 2016 起、
快照评估期自 2017-01-03 起。

后果：在页面上点「重建快照」，构建器按默认 5 年窗口从 ~2021 开始，**2017–2021
会被静默砍掉**，页面「评估期」从 2017 变成 2021，且全链无任何报错。

修复：`datasets.py` 的 CN `l1_factors` 增加 `"build_start": "20170103"`
（与既有快照评估期一致；2016 年为因子回看暖机段）。

## 6. 操作与验收

1. 热加载 api worker（仅杀 8000 端口持有者，非交易时段）。
2. 用 `service.start_build("l1_factors", "CN")` 触发重建，命令带 `--start 20170103`
   （实测日志：`日期 20170103 ~ 20261020 共 2376 天`）。
3. 构建完成（`elapsed_sec=363.0`）后 `GET /api/v1/admin/training-data/fields?
   market=CN&source_dataset=l1_factors` 实测：

   ```
   report_date  2026-10-21
   stale        False
   window       2017-01-03 ~ 2026-10-19 · 2375 交易日 · fwd_ret_5
   matched      110 / 110
   ```

4. 页面刷新后橙标消失，「质量快照 / 评估期」推进到最新。

## 7. 遗留（未做，需另行决策）

- **是否把报告快照重建纳入日更调度**：构建约 6 分钟/库（l1_factors），
  全库批量成本更高，且报告口径变化会影响研究结论；目前保持「手动重建」入口。
  若纳入调度，应先定「哪些库、几点、失败是否告警」。
- 其他 CN 数据集（alpha360 / alpha_library / jq110 / l1_l2 / l2 / tdxgs 等）快照
  仍停在 2026-09-19；它们的评估期均自 2022 起（在 5 年窗口内），一键重建不会
  缩短窗口，但同样需要手动触发才会更新。
