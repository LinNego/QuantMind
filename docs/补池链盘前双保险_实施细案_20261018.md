> 范围：`scripts/alpha_refresh_retry.sh`、`tools/cron/quantmind_pool_chain.cron`、宿主 crontab、相关测试。
> 目标读者：维护盘前数据链与实盘决策轮的人。
> 结论：**盘前增加「链级」自动补跑，三档全在开盘前；同时修掉一个会漏掉北京周一的星期字段缺陷。**

## 1. 事故链与证据

### 1.1 2026-10-13：alpha 内存闸门跳过 → 全链断

1. 02:30 alpha 刷新因「可用内存 14GB < 30GB」整轮跳过，alpha 停在 `dt=20261009`，日K 已到 `dt=20261012`。
2. CUSTOM 重建 fail-closed：「源库分区缺失…拒绝写入」，自定义集停在旧日。
3. 6 个模型推理撞「主模型维度门禁未通过」，候选池缺失。
4. 09:35 决策轮 `rows=0`，`l2.pool_not_member` 拦下全部新开仓；**第一个告警在开盘后才发出**。
5. 由此上线 `alpha_refresh_retry.sh`：宿主 cron 补 alpha → 45G 容器重建 CUSTOM → 池重算 → QQ。
   详见 `docs/补池链硬化_alpha重试_盘前就绪告警_状态卡_细案.md`。

### 1.2 2026-10-16/17：alpha 最新，CUSTOM 在 8G worker 被 OOM

| 日期 | 现象 |
|---|---|
| 2026-10-16 03:00 | CUSTOM 定时任务在 `quantmind-celery`（8G）内 03:01:46 被 cgroup OOM SIGKILL |
| 2026-10-17 03:00 | 同任务、**同一秒数**死亡；alpha360/tdxgs 已写 20261016，jq110 计算中被杀 |
| 2026-10-18（周日） | `no_data_window` 按设计跳过；周末不会自愈 |
| 2026-10-19（周一） | 后台「补池链就绪」卡：kline ok / alpha ok / **custom 20261015** / 推理与池「上游未就绪」 |

根因量级：jq110 = 109 因子 × 925 日 × 5578 只，float64 帧约 4.5 GB，外加中间量；8G cgroup 装不下。
任务 `reject_on_worker_lost=False`，OOM 后不重试 → 静默一天缺口。
2026-10-18 隔离复测确认：同一作业峰值 RSS **7820MB**（基线 274MB），8g 只剩约 370MB——
不是「接近」而是「必然」被 worker 基线或任一并发任务顶破。根治见 §8 第 1 条。
台账与复发点见记忆 `quantcustom-daily-rebuild-schedule`（2026-10-17/18 补记）。

### 1.3 旧重试脚本的盲区

```bash
if [ "$AL_DT" = "$KL_DT" ]; then
    log_line "无事：已最新"
    exit 0          # ← alpha 最新就退出，custom 滞后永远看不到
fi
```

2026-10-17 的形态恰好是「alpha 最新 + custom 滞后」，旧脚本三个档位全部早退，**一次都不会触发**。

### 1.4 星期字段盲区

宿主时钟是 JST（+0900），容器是 CST（+0800）；两者**同一日历日**，仅差 1 小时。
旧 cron 写 `2-6`（JST 周二至周六 = 北京周二至周六），因此：

- 北京周一 04:30/05:30 没有重试；
- 北京周一 07:50 没有盘前就绪检查。

2026-10-19 正是北京周一。**若周一凌晨链路再断，开盘前没有任何自动兜底或告警。**

## 2. 目标与非目标

**目标**

1. alpha 或 CUSTOM 任一落后日K，都在开盘前被自动发现并修复。
2. 修复动作必须**接上下游**（CUSTOM 重建 + 备选池重算），不许只补 alpha 就报成功。
3. 三档重试全部早于 08:00 CST 盘前推理、远早于 09:30 开盘；末档失败必须喊人。
4. 北京周一享有与周二至周五完全相同的覆盖。
5. 尊重用户在调度面板对 CUSTOM 的开关设置。
6. 全部改动有自动化测试；不引入新的外部依赖（宿主不装 redis-py）。

**非目标**

- 不改 CUSTOM 调度的 03:00 主链路（仍由 celery beat 派发）。
- 不改 8G celery worker 的 `mem_limit`（另议，见 §8）。
- 不改推理/决策轮的业务口径。
- 不做跨机器的分布式锁（单宿主单用户 cron，`flock` 足够）。

## 3. 设计

### 3.1 触发矩阵

| alpha | custom | 动作 |
|---|---|---|
| 最新 | 最新 | 静默退出（只记一行日志） |
| 滞后 | 任意 | 刷新 alpha → 重测；成功则进 CUSTOM 判定 |
| 最新 | 滞后 | **跳过 alpha 刷新**，直接进 CUSTOM 重建 |
| 滞后 | 滞后 | 刷新 alpha → CUSTOM 重建 |
| 空（无分区） | — | 与「滞后」同路径（刷新后重测） |

判据基于**分区 `dt=YYYYMMDD` 的最大值**，不依赖 Redis、不依赖 PG：宿主没有 redis-py。
CUSTOM 额外要求该分区内存在 `data.parquet`：写入方先建目录、后写文件（非原子），
SIGKILL 可能留下只有目录的空分区；只看目录名会把它判成「已最新」，自动修复面永不触发。

### 3.2 时间轴（同一行的两个时钟是同一时刻）

| 北京（容器 CST） | 宿主 JST | 事件 |
|---|---|---|
| 03:00 | 04:00 | celery beat 派发 CUSTOM 定时任务（8G worker，可能 OOM） |
| 04:30 | 05:30 | **重试第 1 档** |
| 05:30 | 06:30 | **重试第 2 档** |
| 06:30 | 07:30 | **重试第 3 档（末档，失败推 🟠）** |
| 07:50 | 08:50 | 盘前就绪检查（五段链，断链推 QQ） |
| 08:00 | 09:00 | 容器盘前推理（`auto-inference-window-scan-weekdays`） |
| 09:30 | 10:30 | 开盘 |

alpha 实测 43–53 分钟；第 1 档 04:30 起跑 → 约 05:20 收工 → CUSTOM 约 2 分钟 → 推理约 6 分钟 →
池约 05:30（北京）落地。三档留出「第 1 档撞内存/临时故障」的再试空间。

### 3.3 动作链（幂等）

```
[flock 全局锁]
  ├─ 读 KL_DT / AL_DT / CUSTOM_DT（三次 ls）
  ├─ 都最新 → exit 0
  ├─ dry-run → 打印判断 → exit 0
  ├─ alpha 滞后 → bash alpha_library_refresh.sh（自带 flock / 已最新 / 可写 / 内存四闸）
  │     └─ 重测仍滞后 → 记日志；末档推 🟠 → exit 1
  ├─ CUSTOM 滞后 → docker exec quantmind python3 -（45G）
  │     ├─ 读 Redis 调度配置：enabled=false → SKIP，尊重用户设置
  │     └─ enabled=true → run_market_sync("CUSTOM", cfg)
  │           （唯一实现：三库增量 + 增量守卫 + fail-closed 源库预检）
  ├─ 重测 CUSTOM_DT
  ├─ postmarket_pipeline.py --picks-only（恒重算幂等；缺推理批次时自行补跑）
  │     ├─ rc=0 → 清待办标记
  │     └─ rc≠0 → 写待办标记（后档即使数据已最新也只补池，不许早退）
  └─ 判定：CUSTOM ok 且 picks rc=0 → 🟢；否则记日志，末档/alpha 半途才推 🟠
```

**为什么必须自己接 CUSTOM**：CUSTOM 的定时派发在 03:00，派发标记键
`quantmind:sync_schedule_last_run:CUSTOM:{date}` 一旦置位，当天不再派。
05:30 之后补出的 alpha 不会自动带动 CUSTOM 重建——脚本必须显式调用，
否则就是「alpha 补新、CUSTOM 照旧」的假自愈。

**为什么放在 45G 容器**：jq110 的 1400 天回看窗在 8G worker 里必被 SIGKILL（§1.2 实测两晚）。
`quantmind` 容器 `mem_limit` 45G，实测全量重建 510s、本次补一天 116.5s 通过。

**为什么容器内解释器用 `python3` 而非绝对路径**：镜像只有 `/usr/local/bin/python3`，
没有 `/usr/bin/python3`；2026-10-13 实跑曾因此 rc=127。测试 `test_container_step_uses_container_python_not_host_path` 锁定。

### 3.4 告警语义

| 场景 | 行为 |
|---|---|
| 链本就最新且无待办 | 只记日志，不推 |
| 数据本就最新、仅补池成功 | 🟢「备选池补算完成」（说明上游没动过，只补池） |
| 自愈成功（alpha/custom 至少一段补新，池重算成功） | 🟢 一条，含 before → after |
| alpha 曾滞后，但下游没走完 | **立即** 🟠（链已被动过，不能沉默） |
| 只有 custom 滞后，重建失败 | 非末档只记日志；**末档**才 🟠（避免凌晨连推三条） |
| CUSTOM 调度被用户关掉 | 不推（尊重设置，且没有新数据可庆祝） |
| 末档抢锁失败（前一轮仍在跑） | 🟠「末档未能执行」——这是当日最后的自动兜底，不能静默 |
| 盘前就绪检查 | 独立告警面，带五段链条明细（JST 08:50） |

告警分工的理由：凌晨重试的失败往往下一档就自愈；如果每档都推，值班的人会开始忽略这条告警。
盘前 07:50 的检查才是「今天到底能不能开仓」的最终判据。

### 3.5 并发与幂等

| 资源 | 保护 |
|---|---|
| 重试脚本自身 | `flock -n /tmp/.qm_alpha_retry.lock`；后到者直接让位 |
| alpha 刷新 | 脚本内部另有 flock + 「已最新」早退 + 可写闸 + 内存闸 |
| CUSTOM 增量重建 | `meta.json` 指纹一致时只补缺失分区；重复调用秒退；第 1 档 04:30 起跑，晚于 03:00 主任务（实测 116.5s，文档口径上限 40–60min → 最晚 04:00 收工）；主任务异常拖延到 04:30 之后的并发窗口见 §8 |
| 备选池 | `pick_candidates.py` 恒重算（覆盖写），重复跑结果一致；失败写 `logs/keepers/.qm_retry_pending_picks`，后档只补池 |
| 推理 | 若池脚本发现缺推理批次会补跑；与 04:00 的 picks-only 存在理论重叠，最坏是重复一次推理，不影响数据正确性（`run_id` 唯一键收敛） |

已知边界：重试的 `--picks-only` 与 04:00 的固定 picks-only（`--wait-l2-min 30`）在 L2 迟到时可能时间重叠。
两者都幂等，未加跨脚本锁；若未来观察到重复推理放量，再给两者加同一把宿主锁。

### 3.6 尊重用户设置

容器内的 Python 先读 `quantmind:sync_schedule:CUSTOM`：

- 读不到 / `enabled != true` → 打印 `SKIP: CUSTOM 调度未启用，尊重用户设置不代跑`，退出 0；
- 脚本识别 `SKIP` 后**不重算池、不报 🟢、退出 0**。

这不是「失败」：用户可能故意停掉 CUSTOM 去跑别的研究。代跑会违背显式设置。

## 6. 失败模式与处置

| 现象 | 判读 | 处置 |
|---|---|---|
| 三档都「alpha 仍滞后」 | 内存不足（alpha 峰值 ~24GB）或源数据未到 | 看 `alpha_library/cron_run.log` 的 gate 行；释放内存后手工跑脚本 |
| CUSTOM 重建 rc≠0 且日志含 `源库分区缺失` | alpha 仍缺该日分区 | 先修 alpha，再跑一次脚本 |
| CUSTOM 重建被 SIGKILL（137） | 容器内存也不够（多容器叠加） | 看 `docker stats`；停训练等大内存任务后重跑 |
| 日志 `SKIP: CUSTOM 调度未启用` | 用户关掉了调度 | 若要自动重建，到「数据管理 → A股 → 自定义数据集重建」打开 |
| 三档都没跑 | crontab 丢失 / cron 服务停 | `crontab -l`；备份在 `logs/keepers/crontab.backup.20261018` |
| 日志「CUSTOM 仍滞后」但目录名已是新日 | 分区只有目录没有 `data.parquet`（SIGKILL 残留） | 脚本已按 parquet 判；仍失败则手工删该空分区后重跑 |
| 末档推「未能执行」 | 前一档超过 60min 仍在跑/卡住 | 看进程与 `alpha_refresh_retry.log`；盘前 07:50 检查仍会兜底 |
| 时间看着差 1 小时 | 宿主 JST、容器 CST | 以日志时间戳（JST）与容器日志（CST）分别判读 |

**周末形态**：周六凌晨 CUSTOM 若失败，JST 周六不在 `1-5` 内，不会立即重试；
下一次是**北京周一 04:30** 第 1 档（判据同样是 `custom < kline`），仍在 07:50 检查与 08:00 推理之前，安全。
如希望周六也提前补，可把第 1 档改为 `1-6`，但需接受周六无盘前检查、告警无后续兜底。
