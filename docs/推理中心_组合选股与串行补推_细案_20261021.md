## 0. 结论先行与边界

### 0.1 这次要交付什么

1. **一组"次日上涨命中率"候选组合**：先冻结候选定义与检验协议，再跑离线研究，产出 2–4 个带推荐等级的模板（推荐 / 观察 / 研究）。**不预先承诺某个组合一定最高**。
2. **组合选股 + 调仓计划**：推理中心新增「组合选股」工作区。组合 = 同市场、同特征签名（`factor_schema_hash`）、不同模型架构的截面分位加权。组合来源两条：**系统自动识别**（按签名/周期分组生成候选并给证据等级）与**人工勾选**（同签名同周期）。默认模板 = 现有 13 个 T+10 模型等权（C0）。调仓是**纸面计划**：每日榜单 Top50、每日新进 5 只、持有 10 日滚动，第 10 日建满 50 只；不接券商、不产生委托。
3. **模型治理多选 + 一键串行补推**：治理表支持勾选多个模型，串行逐日补推到最新可用数据日，任务持久化、可取消、可查看逐模型进度。
4. **合规收敛**：推理中心展示面彻底移除「买入/卖出」，统一为位置词（靠前/居中/靠后）；调仓统一为「新进/留存/退出」。

### 0.2 必须先说清的边界

- **本期不训练新模型**。只做"现有模型的组合、排序、调仓"。若要做专门的「次日二分类器」，需要新标签、新训练、独立验收，另立项目。
- **次日命中率不等于可赚钱**。2026-10-20 的证据：单模型可执行口径（t 收盘出分、t+1 收盘成交）2026 最好 T+10 XGBoost 49.9%（基准 48.4%，+3.3pp）；T+5 TabNet 理论 52.8%，可执行掉到 48.5%。且 2026 年 31 个模型的排名多重检验后最小 q≈0.66，**统计上不显著**。
- **tree5 反例不能忘**：按次日命中率把 10 日组合换成 tree5 已被同一套 10 日策略证伪（全 13 Top50 全期 39.2% vs tree5 28.7%，2026 年 20.0% vs 9.3%）。所以本次组合研究必须同时过「10 日调仓闸门」，不能只看次日命中率。
- **默认基线是 C0 = 13 个 T+10 模型等权**（300 特征、同一 schema hash）。如果研究没有任何组合通过检验，C0 就是唯一「推荐」，其余只标「观察/研究」。这不是失败，是诚实结果。
- **纸面调仓**：不接 QMT/TDX/券商，不写订单表，不触发任何执行面。确认调仓只写本地纸面台账。

### 0.3 2026-10-21 追加确认的口径

1. **组合来源双入口**：系统自动判断现有模型里哪些能组合（按市场 + 特征签名 + 周期分组），同时允许人工勾选同签名、同周期的不同模型。**默认优先 13 个 T+10**（C0）。
2. **滚动建仓**：每日榜单 Top50；每日新进 5 只；持有 10 个交易日；滚动建满 50 只；第 11 日起「退出腾位 → 新进 5 只」维持 50 只。
3. **历史标注**：当日榜单每只标的标注前几日的历史选股状态——首次入选日、已持有天数、连续在榜天数、再入选次数。
4. **日期回看**：可选择任意有完整分数的交易日查看当日榜单、滚动建仓视图、调仓计划与历史标注。
5. **可维护**：页面按 `components/combo/` 拆分，展示与管理逻辑分离；词表、分位、评分只保留一份实现；新增市场只改适配器能力位，不在组件里写市场分支。

## 3. 研究设计：次日上涨命中率最高的模型组合

### 3.1 目标与口径（先冻结，再看检验窗）

**目标**：在现有 31 个模型（13 架构 × T+5/T+10，外加 T+20 对照子集）里，找出「TopK 选股的次日上涨命中率」显著高于基线 C0 的组合。

**命中率定义**：

- 理论口径 `hit_theory`：信号日 t 收盘出分，t+1 收盘相对 t 收盘上涨（`close_qfq[t+1]/close_qfq[t] − 1 > 0`）。这是理想成交假设。
- 可执行口径 `hit_exec`：t 收盘出分，t+1 收盘成交，t+2 收盘卖出（`close_qfq[t+2]/close_qfq[t+1] − 1 > 0`）。这是本方案的主指标。
- 可买池：非 ST、上市 ≥60 天、t+1 未停牌、t+1 未涨停；可执行口径额外要求 t+1 收盘未涨停。
- `TopK`：20、50；主指标 `Top50`。
- 组合覆盖：当日有分的成员数 ≥ `min_coverage`（默认 8）。
- 基准：C0（13 个 T+10 等权）同 TopK；另报「同日可买池随机一只」的市场基准作参照。
- 成本：次日策略日换手≈100%，主报告必须同时给 `avg_exec_return` 与扣 6bp（双边 3bp）后的净值；命中率提高但收益不覆盖成本 → 不推荐。

**组合分 S**：成员截面 `percent_rank` 的加权平均；成员缺失时在可用成员间重新归一；`coverage < min_coverage` 的标的不参与排序。**缺失成员不按 0 分处理**。

**展示分**：`S_pct = percent_rank(S)`，再走 `research_score(S_pct)` 得 0–100；位置标签按 `S_pct` 的 30/70 分位。调仓规则仍用 `S`（不是 `S_pct`），两者不要混。

#### 3.2.1 系统自动识别组合（并给证据等级）

系统不训练新模型，只对**已注册、ready、非 ensemble/stacking** 的模型做分组与候选生成：

1. **分组键**：`(market, factor_schema_hash, data_source, feature_count, target_horizon_days)`。同组才允许进入同一组合；这是「同特征」的硬定义，不靠模型名猜。
2. **组内候选**（每组 ≥3 个模型才生成）：
   - `full_equal`：组内全部模型等权（对应 C0/C1）；
   - `family_tree`：树族（LGB/XGB/CAT/RF/TAB）等权（对应 C2）；
   - `family_linear` / `family_dl`：线性族、深度族（组内 ≥2 时）；
   - `consensus_high`：全组等权 + `min_coverage = ceil(0.75 × 成员数)`；
   - `trimmed`：全组去最高/最低各 2 个成员分位后平均。
3. **稳定 ID**：`sys:{signature前8位}:{horizon}:{kind}`。证据更新只改等级，不改 ID，用户收藏/引用不失效。
4. **等级来源**：只读 P1 的 `evidence.json` 中同配置结果；无证据 → `unverified`，默认排在 C0 之后，不显示「推荐」。
5. **默认排序**：`recommended > watch > unverified`，同级按成员数降序；C0（13 个 T+10）恒在第一。
6. **人工组合**：成员必须同组；`purpose=next_day` 允许跨周期但给 `mixed_horizon` 警告；`purpose=rebalance` 强制同周期 T+10。
7. **冲突处理**：人工组合与系统模板同成员时，不合并、不覆盖；人工组合 `source=manual`，模板 `source=system`，列表分两段展示。

### 3.3 切分与统计

- **选择窗**：2025-02-05 .. 2025-12-31（OOS，`split=test` 起点）。
- **验证窗**：2026-01-05 .. 2026-04-30。
- **检验窗**：2026-05-06 .. 2026-08-26（存储预测的公共末端；扩展产物只作敏感性，不进入主结论）。
- **上线影子**：2026-08-27 起用日更 `engine_signal_scores` 累积真实次日命中，样本少，只展示、不参与选择。
- 统计：
  - 逐日配对差（组合 − C0），按月分块 bootstrap 2000 次，95% 百分位 CI；
  - 16 个候选做 BH 多重检验，q<0.10；
  - 月度稳定性：检验窗内至少 60% 月份方向为正；
  - 留一模型：C0 系组合逐个去掉一个成员，最大 Δ 不超过 1.0pp；
  - 功效：检验窗约 80 个交易日，最小可检测效应约 1.2pp（80% 功效），低于此不宣称胜出。
- **数据泄漏披露**：2026-10-20 已看过单模型全期排名；检验窗在单模型层面被观察过。候选定义本次冻结、`C7/C12` 只用选择窗，都是防污染措施；报告必须写明这一点。

### 3.4 判据与推荐等级

**主判据**（全部满足才「推荐」）：

1. 检验窗 `hit_exec(Top50) − C0 ≥ +1.5pp`；
2. 配对 bootstrap 95% CI 下界 > 0；
3. BH q < 0.10；
4. 验证窗 Δ > 0；
5. 10 日调仓闸门：检验窗年化收益不低于 C0 − 2pp，最大回撤不差于 C0 + 3pp；
6. 扣 6bp 后 `avg_exec_return` 不低于 C0，且 > 0。

**等级**：

- **推荐**：主判据全过。
- **观察**：主判据 1–3 过，但 4/5/6 有一项不过；前端可展示，标注「观察，不构成推荐」。
- **研究**：其余；只在证据面板出现，不作为模板。

**若没有任何组合过「推荐」**：C0 为唯一推荐；`tree5/T5/共识` 等标「观察」；前端不得出现「命中率最高组合」的断言，只显示「相对基线的差值及置信区间」。

### 3.5 10 日调仓闸门（防止重演 tree5 错误）

对 `purpose` 含 `rebalance` 的候选，用 2026-10-20 同一套规则在检验窗重跑：

- `S` = 组合分；Top50；持有 10 日；
- 入场 `S ≥ 自身过去 20 日均值`；退出 `S < 20 日均值 − 0.03`；到期退出；
- 每日最多新进 5 只；现金 2%；单票 ≤ 当日 ADV 1%；1000 万；100 股整手；双边万 3；
- 只与 C0 在同一检验窗比较，不复用 20261020 的全期数字。

### 3.7 研究停止/淘汰判据

- **K-R1**：检验窗内 13 个 T+10 模型的有效覆盖 < 90% 交易日 → 停止研究，先修数据。
- **K-R2**：所有候选的相对 CI 宽度 > 4pp → 样本不足，不宣称胜出；只发布描述性统计。
- **K-R3**：C0 在检验窗的 10 日闸门结果比 20261020 全期年化差 > 5pp → 先查数据对齐（T+1、复权、ST、涨跌停），不信任任何组合结论。
- **K-R4**：无候选过「推荐」→ 只上线 C0 + 观察模板，不做「最高命中率」文案。

### 4.3 打分算法（唯一实现）

输入：`blend`、数据日 `T`、参数（`top_k`、`min_coverage`）。

1. **取 run**：按 `(model_id, data_trade_date=T)` 选一条 `status='completed' AND signals_count>0 AND fallback_used=FALSE` 的 run；同日多条按 `signals_count DESC, created_at DESC` 取第一。**排除 fallback 运行**（否则组合里混入别的模型的分数）。
2. **取分**：`engine_signal_scores` 按 `run_id` 取 `symbol, fusion_score`；符号先归一（纯 6 位 → 后缀式给 `stocks`，前缀式给前端）。过滤非有限分数。
3. **成员分位**：每个成员在当日全量分数上算 `percent_rank`（并列取最小名次；`n==1 → 0.0`）。线上用 SQL `PERCENT_RANK() OVER (PARTITION BY run_id ORDER BY fusion_score)`，与 `backend/shared/signal_contract.py::compute_rank_pct` 同口径；研究脚本用 pandas 实现并与其对拍。
4. **组合分**：`S = Σ(w_i × pct_i) / Σ(w_i)`，只对当日有分的成员求和；`coverage = 有分成员数`；`coverage < min_coverage` 的标的不参与排序。
5. **共识门槛**：`consensus_min_count > 0` 时，只保留「分位 ≥0.70 的成员数 ≥ 该值」的标的。
6. **排序**：按 `S` 降序；并列按 `coverage` 降序、`symbol` 升序（确定性）。
7. **展示分/位置**：对通过覆盖门槛的标的算 `S_pct = percent_rank(S)`；`research_score(S_pct)` 得 0–100；`S_pct ≥0.70 → BUY(靠前)`、`≤0.30 → SELL(靠后)`、其余 `HOLD(居中)`。**位置标签不写百分比**。
8. **分歧度**：成员分位的标准差，展示为 低/中/高（固定阈值 0.12/0.22），仅作参考。
9. **贡献**：`w_i × pct_i`，用于证据面板展开。

核心 SQL（当日/窗口共用）：

```sql
WITH runs AS (
  SELECT model_id, run_id, data_trade_date FROM (
    SELECT model_id, run_id, data_trade_date,
           ROW_NUMBER() OVER (
             PARTITION BY model_id, data_trade_date
             ORDER BY signals_count DESC, created_at DESC
           ) AS rn
    FROM qm_model_inference_runs
    WHERE tenant_id = :t AND user_id = :u
      AND model_id = ANY(:model_ids)
      AND data_trade_date BETWEEN :start AND :end
      AND status = 'completed' AND signals_count > 0
      AND fallback_used = FALSE
  ) x WHERE rn = 1
),
scored AS (
  SELECT r.data_trade_date, r.model_id, r.run_id, e.symbol, e.fusion_score,
         PERCENT_RANK() OVER (
           PARTITION BY r.run_id ORDER BY e.fusion_score
         ) AS pct
  FROM runs r
  JOIN engine_signal_scores e ON e.run_id = r.run_id
  WHERE e.tenant_id = :t AND e.user_id = :u
    AND e.fusion_score <> 'NaN'::float8
)
SELECT data_trade_date, model_id, run_id, symbol, fusion_score, pct
FROM scored
WHERE (:symbols IS NULL OR symbol = ANY(:symbols));
```

> 注意：窗口查询里 `symbols` 过滤只用于减少返回行；`PERCENT_RANK` 在过滤前算，分母仍是当日全量，口径不变。

### 4.4 调仓算法（纸面）

参数默认：`capital=10,000,000`、`top_k=50`、`hold_days=10`、`entry_per_day=5`、`target_positions=50`、`cash_buffer=0.02`、`adv_participation=0.01`、`exit_delta=0.03`、`lookback=20`。

**滚动建仓口径**：每日从榜单 Top50 中取 `entry_per_day=5` 只新进，持有 `hold_days=10` 个交易日，滚动建满 `target_positions=50` 只；第 11 日起「退出腾位 → 新进 5 只」维持 50 只。

1. 当日全量组合分 `S_today`（第 4.3 节）。
2. 候选集 = 当日 Top`max(top_k, target_positions)` ∪ 当前纸面持仓。
3. 取过去 20 个交易日（不含 T）的 `S`，仅对候选集算；每个标的需 ≥15 个有效日，否则标「数据不足」。
4. **历史标注**（当日 Top50 每只）：
   - `first_entry_date`：纸面台账中最早开仓日；
   - `held_days`：已持有交易日数（无持仓为 0）；
   - `consecutive_days_in_top50`：截至 T 连续在 Top50 的天数；
   - `last_entry_date` / `reentry_count`：最近一次开仓日与再入选次数；
   - 展示为 `D-3 入选`、`持有 4/10`、`连续在榜 6 天`。
5. **持仓处理**：
   - `S` 缺失 → 留存，标「数据不足，需人工复核」（不强制退出）；
   - 持有天数 ≥ `hold_days` → 退出，原因「到期」；
   - `S < mean20 − 0.03` → 退出，原因「分数退出」；
   - 否则留存。
6. **新进**：不在持仓、当日排名 ≤ `top_k`、`S ≥ mean20`、`mean20` 有效；按排名取前 `entry_per_day` 只。
   - 可新进数 = `min(entry_per_day, target_positions − 留存数)`；不足 5 只就少进，**不降低门槛凑数**。
   - 建仓前 10 个交易日若留存 < 目标，按 `entry_per_day` 逐日补足。
7. **目标金额**：`target_value = min(capital × (1 − cash_buffer) / target_positions, amount_T × 1%)`；`amount_T` 取 QuantDB `daily_unadjusted.amount`（单位万元 ×10000）。缺 amount → 标「容量未校验」，不静默跳过。
8. 参考价：`daily_unadjusted.close`（不复权，仅展示）；缺价 → 不新进，标「无参考价」。
9. 输出三类：`entries / holds / exits`，每条含 `code, name, S, S_pct, mean20, exit_line, target_value, ref_price, held_days, first_entry_date, consecutive_days_in_top50, note`。
10. `positions_hash` = 当前 open 持仓的稳定哈希；确认时校验，防止基于过期持仓生成计划。

**历史日期回看**：

- `GET /{blend_id}/plans?date=YYYY-MM-DD` 返回该数据日的计划；无持久化计划时可即时重算（只读，不写台账）。
- 日期选择器只列出该组合有完整分数的交易日；未来日期禁用。
- 回看时台账按「该日之前已确认的计划」重建，不使用今天的持仓，避免前视。

**确认纸面调仓**：

- 只允许 `data_trade_date` 在最近 2 个交易日内，否则 409「计划已过期」；
- `plan.confirmed_at IS NULL` 且 `positions_hash` 与当前一致；
- 事务内：关闭 exits、按 entries 开仓、写 `confirmed_at`；
- 不写任何订单/委托/成交表。

**实测（2026-10-21，开发机，13 模型 / 300 维 / quantdb_factors）：**

| 接口 | 冷启动 | 热路径 |
|---|---|---|
| 当日榜单 `GET /blends/{id}/ranking`（含历史标注） | ≈5.6s | ≈0.9s |

## 5. 多模型串行补推（后端）

### 5.1 现状问题

旧 `POST /{model_id}/inference/backfill`：

- 任务状态在进程内 dict `_backfill_tasks`，重启即丢；
- 用 FastAPI `BackgroundTasks`，长任务在客户端断开/重启时不可控；
- 不传 `redis_client`，推理锁不生效；
- 无取消、无持久化、无多模型编排；
- 每日 `merge_signals_into_pred` 无并发锁，与批量推理/手动补推同时写同一 `pred.parquet` 会**丢行**（读-改-写，最后写者覆盖）。

新任务层解决这五点；旧端点保留兼容。

### 5.2 任务数据模型

```sql
CREATE TABLE IF NOT EXISTS qm_model_inference_jobs (
```

### 5.3 执行语义

- **串行**：模型按「缺口天数升序、model_id 升序」排队；模型内日期升序；全局同一时刻只跑一天。
- **每天**：
  1. 检查 `cancel_requested` → 停止；
  2. 检查 `batch_inference_orchestrator.is_running(tenant,user,model)` → 该模型标 `skipped_busy`，跳到下一模型（不阻塞整单）；
  3. 取 Redis 推理锁（`REDIS_DB` 默认 0，与 trade runner 同库；**不要用 db3**，否则锁是空转）；
  4. `InferenceScriptRunner(primary_model_dir=storage_path, primary_model_id=model_id).execute(date, tenant, user, redis_client=redis_client)`（线程池内同步执行）；
  5. 成功 → `merge_signals_into_pred` 逐日合并 + 更新计数；失败 → 记 `failed`，**不中断该模型的其他日期**；
  6. 同一模型连续失败 3 天 → 该模型标 `failed`，跳到下一模型（避免在坏模型上耗几小时）。
- **锁被占**（`fallback_reason=LOCK_HELD`）：记 `skipped_lock`，不算失败，不重试；最终状态 `partial` 并提示「有同日推理在别处执行，请稍后重跑」。
- **进度**：每完成一天更新 DB（节流 1s）；`heartbeat_at` 每 30s 更新。
- **取消**：`cancel_requested=true`；当前日跑完再停；状态 `cancelled`，`model_results` 保留剩余缺口。
- **重启**：进程重启后，`GET /jobs` 或应用启动时把 `status IN ('queued','running') AND heartbeat_at < now()-10min` 标记为 `failed`，`error='进程重启，任务中断'`；用户重新预览剩余缺口即可。
- **任务引用**：`asyncio.create_task` 必须把 Task 放进模块级 `set` 持有强引用，防止被 GC；不要用 `BackgroundTasks`。
- **ETA**：每模型取最近 10 条 completed run 的 `duration_ms` 中位数，缺省 120s/日；展示区间 `[0.7×, 1.5×]`，不承诺。

### 5.4 共享核心重构（DRY）

新增 `backend/services/engine/inference/model_backfill.py`：

```python
def resolve_backfill_model(tenant_id, user_id, model_id) -> BackfillModel | None
def compute_gap_dates(model) -> list[str]          # 复用 coverage 逻辑
def run_one_day(model, day, tenant_id, user_id, redis_client) -> DayResult
def run_serial(models, tenant_id, user_id, *, progress_cb, should_cancel, redis_client) -> JobResult
```

- `run_one_day` 把「构造 runner → 执行 → 合并 pred → 失败落 run 终态」收拢，旧 `trigger_backfill` 与新任务共用。
- 旧 `POST /{model_id}/inference/backfill` 改为创建单模型 job，返回 `{task_id: job_id, job_id, status, gap, target_dates}`；旧 `GET .../{task_id}` 从 job 表读并映射旧字段（`progress 0-100`、`appended`、`merged_days`、`failed`、`logs` 字符串）。
- 这样 `_backfill_tasks` 可以删除；旧前端 `InferenceCoveragePanel` 行为不变。
- 若用户已有活跃 job，旧端点返回 409，文案指向该 job（不要静默排队）。

### 5.5 `pred.parquet` 并发合并锁（P0 修复）

`merge_signals_into_pred` 目前是「读全量 → concat → 写临时文件 → `os.replace`」。两个不同日期的合并并发时，后写者用旧快照覆盖前者，**丢行且无报错**。

修法：

- 在 `pred_merge.py` 内加**跨进程锁**：`qm:lock:pred_merge:{sha1(absolute_path)}`，Redis 同步客户端（`REDIS_DB` 默认 0），TTL 120s；拿不到锁重试到 120s，超时抛错（不静默丢数据）。
- 同时加进程内 `threading.Lock`（同进程多线程快速路径）。
- 测试：两个线程各合并不同日期（各 100 行）到同一文件，断言两天都在、行数 = 200；再测 Redis 锁 acquire/release 被调用。
- 这是新串行任务的前置条件：串行任务会与每日自动推理、旧补推、批量推理并发写同一文件。

## 9. 停止/淘汰判据（Kill Criteria）

### 9.1 研究

- **K-R1** 数据覆盖不足 → 停止研究，先修数据。
- **K-R2** 所有候选 CI 宽度 >4pp → 不宣称胜出，只发描述统计。

## 10. 风险与陷阱清单

1. **路由遮蔽**：`/models/blends` 是单段路径，必须注册在 `model_training_router` 之前（`main.py:496` 已有先例）。
2. **T+1 错位**：`engine_signal_scores.trade_date` 是生效日 T+1；必须经 `run_id → qm_model_inference_runs.data_trade_date` 映射回 T。
3. **`rank_pct/score_rank` 不可信**：推理脚本写入恒 NULL；一律现算 `PERCENT_RANK`。
4. **同名多 run**：同 (model, date) 可能有多条；按 `signals_count DESC, created_at DESC` 取一条，并排除 `fallback_used=TRUE`。
5. **符号三套口径**：信号表纯 6 位、`stocks` 后缀、前端前缀；用 `StockCodeUtil` 一处转换，单测覆盖 6 位/前缀/后缀/非法。
6. **缺失成员不能当 0 分**：否则组合分被稀释；必须重归一 + 覆盖门槛。
7. **`pred.parquet` 并发合并丢行**：现有代码无锁；先加 Redis + 线程锁（P0），再上串行任务。
8. **进程内任务状态**：新任务必须落库 + heartbeat + reaper；`asyncio.create_task` 要持强引用，不用 `BackgroundTasks`。
9. **锁库不一致**：推理锁与 trade runner 都用 `REDIS_DB` 默认 0；若用了 db3，锁是结构性空转（与 QQ 速览 db0/db2 陷阱同类）。
10. **`LOCK_HELD` 不是失败**：计为 skipped，最终 partial，提示稍后重跑；不要自动重试到死。
11. **批量推理碰撞**：同一模型可能正被 `batch_inference_orchestrator` 跑；先 `is_running`，忙碌则跳过该模型。
12. **系统模型只读**：串行任务排除；组合可包含（组合只读分数，不推理）。
13. **调仓只用 T+10**：v1 强制；T+5/T+20 组合只做次日观察，不生成调仓计划。
14. **`S` 与 `S_pct` 不要混**：调仓阈值用 `S`（成员分位均值），展示分/位置用 `S_pct`（组合内分位）。
15. **ADV 单位**：QuantDB `amount` 是万元，×10000 才是元；1% 参与率算错会把买单截成 0 股。
16. **A 股红涨绿跌**：分数/收益用红绿；位置标签用中性色，避免「靠前=红=涨」的暗示。
17. **不写「前 20%/后 20%」**：`signal_side` 两条生成路径；组合位置只给定性标签。
18. **证据不现算**：前端只读 `evidence.json`；缺失显示空态，绝不在前端硬编码命中率。
19. **研究泄漏**：候选定义先冻结；`C7/C12` 只用选择窗；检验窗只评估一次；报告披露单模型层面已观察过检验窗。
20. **容量/健康**：研究脚本要求 `MemAvailable > 6GB`；调仓计划生成与推理/训练不要同时跑（宿主内存紧张，见 20261021 记忆）。
21. **HK/US 符号未验证**：本期只开 CN；适配器能力位控制，不做「看起来能跑」的伪支持。
22. **旧前端轮询上限**：`InferenceCoveragePanel` 120×2s；新弹窗不要复用该上限，长任务要能恢复。
23. **计划过期**：数据日超过 2 个交易日禁止确认；避免用旧价格写纸面台账。
24. **并发确认**：`positions_hash` + `confirmed_at IS NULL` 双校验；事务内完成。
25. **部署**：改动后 `npm run typecheck` → `bash scripts/deploy_frontend.sh` → 浏览器强刷；不要走 `web/dist` 老路。

## 14. 上线前评审结论（2026-10-21）

已修复（均有回归测试）：

- **HIGH** 串行补推回调契约：`_should_skip_model` 必须是 `async`（`run_serial` 会 `await`）；同步实现会让所有任务在第一日前直接 failed。
- **MEDIUM** PATCH 静默丢权重：只给 `weights` 不给 `model_ids` → 400 `weights_require_members`；改用途为 rebalance 时对存量成员重跑 T+10 闸门；改名撞唯一键 → 409（与新建同口径）。
- **MEDIUM** 极端 `data_trade_date`（9999-12-31 / 0001-01-01）会让交易日历兜底 `day+1` 溢出成 500 → 入参拦成 400。
- **MEDIUM** 计划确认窗口错位：原先前端按 `/dates` 序位判过期，缺评分日时与后端「最近 2 个交易日」口径不一致，且依赖浏览器时钟。现在服务端返回 `can_confirm`，前端只消费该字段（缺失才退回序位兜底）。
- **MEDIUM** 归档组合占用唯一名：`(tenant_id,user_id,name)` 不区分 status，默认组合归档后自动创建会永久 409 → 唯一冲突且既有行 archived 时原地重激活（复用原 blend_id，台账不断链）。
- **LOW** 取消与开跑竞态：`queued → running` 改为条件迁移（`claim_running`），取消先落地时不再被 worker 覆盖。
- **LOW** 确认行数：先抢 `confirmed_at`（rowcount 0 → 409）再写持仓，避免「未确认却写入台账」。
- **LOW** 补推弹窗轮询：请求序号 + mounted/open 守卫，终态后的迟到响应不会把界面拉回运行态；关窗后异步 continuation 不再起定时器。
- **LOW** 组合无评分日时 rolling/plan 的 loading 标志会永久转圈 → 空分支显式复位。

遗留（availability / 架构，未在本期处理）：

- 组合榜单/滚动/计划/预览在 async handler 内同步读 DuckDB/parquet，重查询会阻塞事件循环；后续用 `asyncio.to_thread` 包住因子读取，并给重端点加限流。
- `_window_cache` 是进程内缓存：多进程部署时会重复计算（OSS 单容器可接受）；跨进程缓存需落 Redis。
- 串行补推只有「每用户单活跃」约束，无全局并发上限；多用户同时触发时仍可能争抢引擎资源。
- `_run_job` 对预览后被判为不可补推的模型是静默 `continue`（全部剔除时任务 failed 并提示「没有可补推的模型」）；后续把逐模型跳过原因写进 `logs`。

## 15. 部署态排障记录（2026-10-21 盘中）

现象：新前端（`main-12Zp1FDS.js`）打开「组合选股」时左栏显示「暂无已保存组合 / 暂无可用模板」，右侧榜单报 **`Model not found`**。

根因：**前端先于后端更新**。新前端请求 `/api/v1/models/blends/*`，而运行中的 API 进程仍是旧版本，没有挂组合路由；`model_training` 的 `GET /api/v1/models/{model_id}` 参数兜底把 `blends/...` 当成 model_id，返回 404 `Model not found`。这不是资格筛选把模型排除了——直接调用服务层的结果是：可参与 101 个、13 个 T+10 模型同组（C0 基线）、38 个自动模板、证据等级 `research`。

前端硬化（本次提交 `fa4286de`）：

- `blendErrorMessage` 将该形态的 404 映射为「组合选股接口未就绪：当前后端为旧版本，请更新后端后重试」；
- 工作区清单/模板读取失败时不再谎称「暂无」，显示「组合清单读取失败 / 模板读取失败」，并提供「重新加载」；重试会复位默认组合的自动创建守卫；
- 构建器读取失败时隐藏「没有可参与组合的模型」空态，改为错误详情 + 重试。

P6 探针同时修正了三处环境相关的盲点：

- 首启「投资适当性评估」弹窗会拦截点击 → 先点「稍后再答」；
- 推理中心顶栏是普通按钮不是 antd Tabs → 选择器同时兼容 `button` / `[role=tab]`；
- 「一键推理至最新」只在勾选 ≥2 个模型后出现 → 探针只勾选两个模型再断言入口可见，不启动补推。

部署顺序结论：**后端热重载完成前，组合选股只有诚实失败态，没有数据**；后端进程切换到新代码后（非交易时段执行），同一份前端无需再发版即可出榜单。
