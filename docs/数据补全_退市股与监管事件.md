# 补数据：退市股 & 监管风险事件

> 日期：2026-11-01 ｜ 产出：`scripts/fetch_delisted_universe.py`、`scripts/fetch_regulatory_events.py`
>
> 解决的问题：**回测的股票池只有「现在还活着」的 5,228 只**，退了市的票从来不在池子里；
> 而低价小市值恰恰是退市率最高的区域。不补这块，所有收益数字都是上限。

---

## 一、退市股：缺多少、怎么补、影响多大

### 1.1 缺口有多大

| 项 | 数值 |
|---|---|
| QuantDB 里的标的 | 5,228 只（全部活到 2026-10） |
| 2016-01 ~ 2026-10 实际退市 | **272 只** |
| 其中**沪深主板** | **210 只** |
| 主板年均退市 | 19.6 只（2024 年峰值 46 只） |

按年分布（主板）：

| 2016 | 2017 | 2018 | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 2025 | 2026 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 4 | 5 | 11 | 10 | 20 | 37 | 34 | **46** | 25 | 17 |

### 1.2 这些票退市前是什么样（实测 210 只主板退市股）

| 区间 | 中位跌幅 | 大跌占比 |
|---|---|---|
| 退市前最后 20 个交易日 | -0.0% | 20% 跌超 50% |
| 退市前最后 120 个交易日 | **-78.7%** | 85% 跌超 50%、47% 跌超 80% |
| 退市前最后 250 个交易日 | **-80.5%** | 87% 跌超 50%、53% 跌超 80% |

- **退市前最后收盘价中位数 0.43 元**（面值退市），最低 0.14 元；
- 退市前 12 个月的**平均单月收益 -8.0%**，最差单月中位 **-60%**。

**这正是「低价小市值」策略的建仓区**：几毛钱、十几亿市值、日成交两千万——
每一条都符合本文策略的选股条件，但数据库里根本没有它们。

### 1.3 怎么补（已实现）

```bash
python scripts/fetch_delisted_universe.py --since 2016-01-01 --lookback 730
```

- **退市名单**：`akshare.stock_info_sh_delist()` / `stock_info_sz_delist()`（交易所口径，带退市日）
- **日线**：`baostock`（唯一实测能稳定取到已退市代码的免费源），后复权 + 不复权两套价格
- **产出**：`data/delisted/delist_list.parquet`（272 只）+ `data/delisted/daily.parquet`（120,845 行 / 249 只，含退市前 2 年）
- 单次全量约 9 分钟，支持断点续跑（每 25 只落一次盘）

失败过的路径（记录下来省下次踩坑）：

| 数据源 | 结果 |
|---|---|
| 东方财富 `ak.stock_zh_a_hist` | 本机到 `push2his.eastmoney.com` 不通（代理/直连都失败） |
| QuantDB 自身 | 退市股一行都没有 |
| `instrument_detail` | 只有当前快照，5,581 行里仅 1 只 `IsQuitGP=1` |
| **baostock** | ✅ 可用，002509 最后 0.15 元、300156 最后 0.12 元，都是真实退市价 |

### 1.4 影响量化：年化要高估 2–4 个点

用「每月等概率持有 1 个月、单票权重 1/40」估算单次退市事件的拖累：

- 单次期望拖累 = 退市前平均单月收益 -8.0% ÷ 40 = **-0.20%**
- 主板年均退市 19.6 只

| 假设 | 年化拖累 |
|---|---|
| 退市股全部会进入小市值池 | **-3.9%** |
| 一半会进入（更保守） | **-2.0%** |

**结论：主板 40 只满仓口径的年化 17.68%，真实值大概 14%–15.5%；
回撤 -39.81% 也会更深**——因为退市集中在 2024 年（46 只），正好是微盘踩踏那一年。

> 为什么不能简单"加进选股池重跑"：退市股缺 `total_mv`（`features_daily` 里没有它们的行），
> 而市值是本文策略唯一的排序字段。要么补股本数据自己算市值，要么用上面的敏感性口径。
> 我选后者——它不需要额外假设，且给出了上下界。

## 二、监管风险事件（立案调查等）：库里有什么、缺什么

### 2.1 库里已有的

| 位置 | 内容 | 覆盖范围 |
|---|---|---|
| PG `news_article_enrichment` | `tickers[]`、`event_tags[]`、`sentiment_label/score` | **仅平台运行期间抓到的新闻**（Huntly RSS → enricher），不是 10 年历史 |
| `backend/services/api/news/report_match.py:52` | `EVENT_TAG_RULES` 关键词表 | 规则，不是数据 |
| `skills/news-sentiment-research/SKILL.md` | 已做过验证：**「监管/立案调查利空真实有效 ★3」**，T+5 平均 **-2.67%** | 结论，可直接引用 |

**事件标签已经覆盖你要的那几类**（源码原文）：

```python
("立案",     "立案调查", "bearish"),
("立案调查", "立案调查", "bearish"),
("警示函",   "监管",     "bearish"),
("监管",     "监管",     "bearish"),
("处罚",     "监管",     "bearish"),
("违规",     "监管",     "bearish"),
("退市",     "退市风险", "bearish"),
("问询函",   "监管",     "bearish"),
```

**但三个问题让它做不了回测**：

1. **只有平台跑起来之后的数据**（RSS 抓取从部署那天开始），没有 2016-2025 的历史；
2. **新闻 ≠ 公告**，「收到证监会立案告知书」这类硬事件，公告口径最全，新闻经常漏；
3. PG 现在没跑（容器 `quantmind-db` 已停止），查不了。

### 2.2 怎么补（已实现）

走**公告**：东方财富公告库按日拉全市场，按标题关键词归类。

```bash
python scripts/fetch_regulatory_events.py --start 2016-01-01 --end 2026-10-23
```

产出 `data/regulatory/events.parquet`：`symbol / announce_date / category / title`

事件分类：

| category | 关键词 | 说明 |
|---|---|---|
| `investigation` | 立案 / 立案告知 / 立案调查 | 最强利空 |
| `penalty` | 行政处罚 / 警示函 / 监管措施 / 通报批评 / 公开谴责 / 违规 | 次强 |
| `inquiry` | 问询函（剔除「回复」类） | 弱 |
| `delist_risk` | 退市风险 / 终止上市 / 面值退市 | 直接对应退市 |

**实测样本（2023-01-03 ~ 2023-03-20，50 个交易日）**：

| 类型 | 事件数 | 涉及标的 |
|---|---|---|
| penalty | 317 | 272 |
| delist_risk | 294 | 79 |
| inquiry | 147 | 83 |
| **investigation** | **37** | **29** |

即**立案调查约 17 件/月（≈200 件/年）**，按去重标的口径约 140 只/年——占全市场 2.7%。
抓到的标题长这样（真实数据）：

```
力源科技:关于收到中国证券监督管理委员会立案告知书的公告
紫鑫药业:关于公司及原实际控制人收到中国证监会立案通知书的公告
*ST奇信:关于持股5%以上股东收到中国证监会立案告知书的公告
```

⚠️ **两个坑**：

1. **吞吐慢**：`stock_notice_report` 每天要翻 10+ 页，约 5 秒/天；10 年 ≈ 2,500 个交易日 ≈ **2.5 小时**。
   建议分批跑（脚本支持断点续跑，已抓过的日期会跳过）。
2. **噪声多**：北交所 IPO 审核问询函会混进来（标题含"审核问询"），脚本已用 `NOISE` 词表剔除，
   但建议入库后再按"代码是否已在 QuantDB"过滤一次。

### 2.3 怎么用进回测

有事件表之后，在选股前加一条：

```python
# 剔除过去 N 天内出现过监管事件的标的（N 建议 120~250 个交易日）
bad = events[(events.announce_date <= 信号日) &
             (events.announce_date >= 信号日 - N) &
             (events.category.isin(["investigation", "delist_risk"]))].symbol.unique()
pool = pool[~pool.symbol.isin(bad)]
```

**必须只用 `announce_date <= 信号日` 的事件**——公告日期就是信息可见日，用未来的公告剔除等于作弊。

## 三、建议的推进顺序

1. ✅ **先补退市股**（已完成取数）——这是所有结论的地基，不做的话后面每个因子都会被高估 2–4 个点；
2. **把退市股真正并进回测**：需要补股本（`total_shares`）来算市值，或者接受敏感性口径；
3. **再建监管事件表**（2.5 小时，可后台跑）；
4. 最后才是研究新因子——**在虚高的基线上找因子，找到的都是假的**。
